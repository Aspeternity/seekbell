# 分阶段开发计划

每阶段交付可审阅提交、检查结果、限制和下一步；更新状态文件。先读实际仓库，若空仓库则按以下顺序建立。

|阶段|范围|退出条件|
|---|---|---|
|M0 工程基线|核对环境；后端/前端骨架；锁文件；基础CI；数据库迁移；版本展示|前后端构建与基础检查可复现，README记录真实命令|
|M1 核心闭环|NodeSeek解析、基线、帖子身份、规则引擎、持久化outbox、模拟通知|无真实网络样本测试通过，重复摄取/崩溃恢复不丢投递意图|
|M2 四种通知|TG/Bark/SMTP/Webhook、目标配置、业务响应检查、重试和按目标合并|模拟故障矩阵通过；用户提供目标后分别完成真实投递验证|
|M3 Web管理|初始化、认证、六个页面、条件组、历史/手动测试、暂停语义|核心浏览器流程验证；不存在假按钮或不可用开关|
|M4 部署恢复|Docker/Compose、反代、GHCR流程、备份恢复、迁移、日志/健康检查|固定SHA镜像可启动，重启/恢复/升级演练通过|
|M5 实机验收|PVE Docker VM真实RSS、授权目标、页面体验、运行观察|验收记录完整、已知问题有处理结论；用户确认后正式发布|

远程依赖不应阻塞本地阶段：没有仓库Owner、SSH或通知凭据时使用本地Git和模拟测试，明确记录对应真实验证未完成。不得为了完成表格伪造通过。

持续运行24小时可作为M5建议观察周期，不是已确认的服务SLA；期间统计采集成功/错误、延迟样本、投递结果，不进行压测或主动制造论坛帖子。

## 检查点要求

每个有意义的改动/测试/阻塞后更新PROJECT_STATE，而非只在阶段结束时更新。换对话按CODEX_START执行。验收门禁不得为节省token跳过；重复读取和无变化的重复验证不作为工作量目标。已完成阶段详细记录可归档docs/history，当前状态保留链接。
