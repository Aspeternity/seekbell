# Linux DO 热榜错峰方案（随v0.6.1发布）

日期：2026-11-07（Asia/Shanghai）。用户确认按下列4点实现，并确认偶发失败的提示改法；之后用户暂缓“关于与诊断”改版，要求先修此问题。代码基准fd310e5，随v0.6.1发布。

## 根因与证据

现用实例（0.6.0）周榜常显示“Cloudflare验证”。核心原因是热榜预热按2秒间隔连发，而周榜通常排在最后，并非周榜地址本身有问题。

- 三榜默认每小时共7次请求（热门4、每日2、每周1），采集最快每小时60次，问题是扎堆而非总量。
- 11/03 23:40启动后：00:26:48每日、00:26:51热门成功，约00:26:53周榜被挑战；00:31:57周榜单独重试成功。
- 倒序对照（11/04）：00:45:15周榜、00:45:16 RSS、00:45:18每日均成功，00:45:21热门429+cf-mitigated=challenge。被挑战的是连发中的第4个请求。
- 5秒间隔实测（3轮，相隔6分钟）：第1轮三榜全200，但RSS在13秒内第4个请求时被挑战，采集停约5分钟；第2、3轮同密度通过。
- 结论：挑战出现在约6～13秒内≥3个Linux DO请求时，但同密度也可能通过；窗口无法从外部测准，5秒不够。不再做触发实验（每次挑战会使采集停5～10分钟）。
- 11/03 14:54～16:16 RSS每分钟单独请求也被挑战9次，属IP整体被挑战，错峰不能消除。本机WSL同节奏一次全200，未复现。

## 已确认方案

1. 后台错峰：未在看的榜每轮只刷一个，且距上次Linux DO请求≥30秒。Linux DO采集最小间隔60秒，不会饿死。
2. 在看榜优先：任意15秒内最多2个Linux DO请求，15秒内将到期的采集也计入；采集本身不限速，只计数。判定：最近15秒请求数＋采集即将到期(0/1) ≤ 1 时才可发热榜请求。
3. 等待不改状态：错峰等待不写deferred/error_code/next_attempt_at，看板tag不变，不触发长轮询、不显示提示；warm_once的下次唤醒时间要算入错峰时刻。
4. 切榜唤醒：PUT /api/manage/hotlists/selection调用touch(nudge=True)或等效逻辑，刚切到的已过期榜进入在看优先；现状最多等WARM_TICK=60秒。
5. 失败提示：有快照且快照未超过2倍刷新间隔时，不显示失败/Cloudflare横幅，只保留“获取于”；超过后恢复现有提示。无快照仍照常提示。这改变SPEC 6.1“失败有旧快照时保留并标明”，实现时一并改。
6. 加热榜失败脱敏日志（只记站点、周期、固定错误码）。

## 实现位置

- `services/request_budget.py`：`reserve`是采集、手测、热榜的共同入口，在此记录Linux DO请求时刻。用内存`deque`即可，无迁移。
- `services/hotlists.py`：`_warm_site`一轮只启动一个；`_ensure`区分在看/后台；`_policy`把采集到期判断从2秒扩到15秒；`_render`按快照年龄决定是否暴露失败。
- `api/hotlists.py`：保存选择时唤醒。
- `CommunityHotlist.vue`：只有状态语义变化时才动，现有等待文案保留给无快照场景。
- 文档：与代码同一提交改SPEC 6.1/6.2（第125行“至少2秒”）/6.6、ARCHITECTURE末节、CHANGELOG。

## 效果与限制

- 隔很久打开时：立即显示旧榜，当前榜马上刷新，其余约30、60秒内静默替换。
- 切到无快照的榜（罕见）最坏多等约15秒。
- 不能消除IP整体挑战；“15秒2个”是经验值，只能大幅降低概率。
- 已排除：Cookie、浏览器模拟、第三方转发（SPEC禁止）；ETag（不减请求次数）；全局5秒间隔（实测不够）。
