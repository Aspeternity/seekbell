## 建议结论与范围

采用“一个公开最新主源＋按任务汇总的官方节点订阅＋独立热门/目录”。主源是匿名API V1 topics/latest.json；指定节点使用官方JSON Feed feed/{slug}.json，全部来源转换成同一规范帖子，统一匹配和去重。节点仍仅在任务内配置，不增加网站级节点总范围，也不让用户填写任意URL。

这比原方案多了必要的有限多来源调度、源内基线与站级去重边界，目的是满足指定节点需求；不能把旧方案的节点过滤包装成独立节点监控。首版不加Token/登录/Cookie/浏览器/第三方转发，不取主题详情/回复，不增加Redis、搜索服务或依赖。RSS两站原有来源与语义保持。

内容仅取列表/Feed随附字段，HTML转纯文本最多2000字符并标“接口/订阅摘录”；不承诺全文。V1官方使用说明对将API输出填充商业/个人网站有限制；应按实际保存/展示用途核对，不凭匿名200判断许可，不建设公开镜像。此边界和RSS-only扩为固定官方JSON来源仍待批准。

## 证据与覆盖边界

官方资料：
- V1接口说明：https://www.v2ex.com/p/7v9TEc53。最新接口对应首页“全部”页签，热门对应首页侧栏榜单；不能据名称推断完整全站流。
- 官方节点RSS/JSON Feed规则：https://blog.v2ex.com/rss/。
- JSON Feed官方v1规范：https://www.jsonfeed.org/version/1/。author.name不保证是网站用户名，author.url也需校验；不能直接把格式中的作者字段当作精确身份。
- API 2.0说明：https://www.v2ex.com/help/api。需要PAT，本版不接。
- Livid历史公告：https://www.v2ex.com/t/114919。2014年曾将部分节点排除首页；只能证明设计上的覆盖差异，不能将当时登录要求当作2026现状。
- 当前VPS/二手节点页有官方订阅入口：https://www.v2ex.com/go/vps 和 /go/all4all。

既有一次性匿名实测：index.xml为Atom50项，无独立节点；现RSS2解析器不能直接换URL。latest API当次36项均有member/node，均在Atom50项中；相差14项可能只是窗口差异，不能当作“漏了14个节点”。热门10项、目录1378项约794KB，均为时点事实；index.json为404。API曾有600额度头，旧V1说明120/小时、当前V2说明600/小时；有效额度、缓存旧头和本应用保守编排要区分。

本轮在SeekBell-Dev使用现有HTTPX/HTTP1.1、无Cookie、无重定向各一次读取主源及三个节点Feed，已结束，无持续轮询：
- latest：200、本次36项，节点分布是有限样本；其中未出现VPS/二手不能证明永久排除。
- feed/vps.json与feed/all4all.json：均200、JSON Feed v1、各50项；均有title、id/url、author、date_published、content_html，author字段含name/url/avatar；本次按发布时间降序。字段存在不等于用户名身份或未来排序已完成长期验证。
- feed/programmer.json：ReadTimeout；没有自动换域/重试，须在后续真实验收中复核，不宣称所有节点可用。
- 两个节点Feed Cache-Control为max-age=1800；主源仍可为432000但内容较新。缓存头不是客户端采集周期，也不能仅凭该值推断实际更新间隔或保证即时性。禁止靠随机参数/自动换域规避缓存和访问限制。
- 私有证据acceptance/2026-10-24-v2ex-proposal/optimization-feed-probe.json，只保存状态/计数/字段/响应头/节点分布等元数据，无正文、用户名或帖子ID样本入Git。此前三个probe文件保留。

公开源可能窗口有限、延迟、删除或不包含某些权限内容。节点目录存在、偶尔在主源见过、一次Feed200，均不是完整覆盖保证。新节点来源有“待首次连接/可读取/等待重试/不可用”等实际状态；不凭短期没帖子标“不支持”。

## 任务交互与来源生命周期

任务仍使用每站独立的“不限节点/指定节点”，V2EX候选区本地搜索、限高、已选置顶和已选筛选，分页50条/跨页保留，稳定node.id存值，名称/slug展示。说明：
- 不限节点：对当前已接入的公开内容不限制节点；不表示遍历全站所有节点。
- 指定节点：只匹配所选节点，并为其启用独立官方订阅。可标“独立订阅，约10分钟检查一次”，同时注明实际到达受来源缓存影响。
- 所有启用任务的指定节点按node.id取并集，一个节点只采一次；10个任务选择同节点仍只有一个请求来源。新增任务不会产生整套重复采集。
- 工程候选首版最多10个不同的活跃定向节点，保留20%的保守请求余量；不是官方限制。保存前展示“本次涉及N个独立节点”，超出容量或频率预算明确阻止并说明需减少节点/调长间隔，不静默丢弃/自动降成纯主源过滤。其他两站及通用规则64项上限不变。
- 只有使用该节点的启用任务才维持其专用来源；最后一个任务停用/移除后停止请求，保留来源账本。网站暂停则所有来源暂停；重新启用的来源按既定主动恢复语义重建自身基线，普通进程重启保留状态。
- 不增加网站级节点勾选。网站配置只读展示主源和节点订阅数量/状态，管理范围仍在任务里。当前指定节点可在详情看到“被哪些任务使用”，避免停用误解。
- 不限节点任务会看到当前所有有效来源实际采到的内容；新增/移除定向来源可能改变可见覆盖，界面明确这一点，不能宣称不限节点任务始终拥有固定全站覆盖。

目录只是编号、名称、slug索引，成功快照持久化，24小时按需刷新，失败用旧目录；不定时抓千余节点、不逐字请求V2EX。目录与帖子返回的node可补充标签，目录暂缺/改名不删已选、不变成全部。创建Feed来源必须有经校验的id→slug映射，未解析节点显示等待目录，禁止拼接未经验证的用户输入。父节点不隐式包含子节点。

## 默认频率、预算与状态

|用途|端点|工程默认|
|---|---|---|
|公开最新主源|/api/topics/latest.json|120秒，全部任务共享；最小60秒但受整体预算校验|
|活跃指定节点|/feed/{validated_slug}.json|600秒，错开请求，不并发齐发|
|社区热门|/api/topics/hot.json|900秒按需，只有“热门”，不伪造日/周|
|节点目录|/api/nodes/all.json|24小时按需，手动更新10分钟冷却|

10个节点在默认值下，主源约30次/小时、节点约60次、热门最多4次，约94次，加偶发目录/连接测试。这是计划量，不是官方配额承诺；缓存命中/304不当作免费请求，本应用每次实际出站均纳入本地预算。按旧V1的120次/小时保守设定自动计划量不超过80%（96次/小时），有效更低额度或服务器等待优先；看到600或缓存较高Remaining不自动提高频率。同IP还有其他程序，不能保证从不429。缩短主源间隔时必须重新核算容量，不能允许60秒＋10节点等组合绕过预算。

站内单请求、至少2秒间隔并持久记录等待；各采集源错峰、公平获得时间，采集优先于热榜/目录，真实手测最多每60秒一次且不能耗尽采集预留。限额不足就展示等待与下一计划时间，不伪造解析失败；禁止重复点击、重启或换入口跳过服务端等待。403/访问挑战与429/Retry-After按站政策共享；某节点404/解析失败只影响自身。普通网络/5xx按来源退避，带服务器等待指令则保守共享；原Linux DO已确认退避/手测语义保持。

连接测试默认只检验公开主源，明确结果范围，不一次打完所有节点。网站分开显示主源、节点订阅、目录、热门状态；节点或热榜失败不假称全部监控不可用，主源成功也不掩盖部分节点失败。热榜保留成功快照、失败标时间；真正刷新/限流等待/失败分开，显示下一计划而不保证届时一定恢复。

新帖/节点检查间隔在网站来源设置，热榜间隔在独立热榜设置，目录采用内置低频策略。普通用户使用推荐值；高级自定义先校验最小值、活跃来源总量及预算，不展示复杂CDN/额度字段作为日常配置。

## 多来源一致性与内容语义

这是新版必做项，不能只增加URL：
1. (website_id,post_id)仍为内容唯一身份；来源身份和源内已见/基线另存。来源注册、任务保存、容量校验需事务一致，两个并发编辑不能越过上限。
2. 新节点首次只建立它自己的基线，不推历史；不能清空主源/其他节点基线，也不能先写全站Seen导致主源稍后应处理的新帖被吞掉。源内基线条目与站级真正摄取账本区分；基线条目下次出现仍不得作为新帖。首次全站启用、主动恢复与普通重启分别验证。
3. 同帖从主源和节点两边进入，真正摄取最多一次，合并适用任务；既有站级Seen/Delivered及outbox唯一约束继续生效。单进程仍需事务处理先后到达，不能只依赖内存去重。源内账本增长按稳定数据保留策略，不因清理可读历史重推。
4. 每条内容/采集记录能追溯实际来源，某一源的失败或基线不能阻止其他有效来源处理；暂停/删除的节点来源不继续出站。热榜和目录永不进入监控摄取。
5. API与Feed统一规范URL提取合法主题ID，保留首次快照，不因后续回复/编辑/多来源更完整内容重推或追溯改判。任务增加节点不重扫既有历史。
6. 条件请求按具体来源URL保存；ETag/Last-Modified仅在解析及摄取事务成功后提交。304只更新成功/计划，不写帖子/命中/队列；无有效验证器或需要新基线时不能用304冒充基线。手测不写采集验证器，目录/热门304仅更新已验证快照的新鲜时间。

字段：API member.username是规则用户名；Feed author.name只是展示，必须从已验证的本站/member/{username} URL获取身份并校验，无法确认时保留缺失、说明能力，不把任意显示名当用户名。节点由受信源绑定的稳定node.id确定，Feed本身缺tags不从标题猜。created/date_published用于发布时间，date_modified/last_touched不当新帖时间。删除/缺合法ID等条目隔离，异常批次不伪造成成功。正文仅实际附带内容转纯文截2000，缺失/空值分开，精确作者或仅摘要条件沿用三值判断；混合Linux DO任务的作者限制保持。

诊断分开回答“是否采集到→是否有字段→规则是否匹配→通知是否送达”。未找到帖子只能显示“当前未采集到，暂不能判断匹配”，不杜撰未命中原因；可跳转来源状态看窗口缺口、限流及节点订阅情况。复用现有possible_gap：前后窗口完全无交集仅提示可能缺口，不声称确切漏帖数量。先保持固定周期，不做未经验证的复杂自适应或补抓历史。

## 实现与交付边界

新增JSON获取/两种结构映射与纯V2exAdapter，复用HTTPX、公网读取约束、HTML转纯文和现有模块。API数组与JSON Feed对象显式校验，Feed version/固定host/来源绑定/MIME/identity编码/超时/1MiB列表上限；目录单独2MiB及项数上限，不放宽其他RSS的XML安全策略。不为此开发Atom解析或使用V2 Token。无新增Python/前端依赖，SQLite、单服务进程、单容器保持。

当前SourceRunner/source_probe/网站状态等多处仍假设一站一源或rss_url；须做受限的来源注册/采集格式声明与V2EX来源协调，逐项移除不适用假设，旧两站仍各一个固定来源。WebsiteRequestBudget原硬编码linuxdo，按站实例/策略隔离；不建设通用分布式队列、任意插件或全站节点爬虫。

候选迁移0017新增默认关闭的V2EX、源/目录/HTTP验证器和必要源内账本；原网站、任务版本、安装顺序、凭据、历史和队列不重写，不自动给旧任务添加V2EX。动态来源只从受管理任务产生。实际迁移号在开发前复核；备份0016整卷并在隔离副本验证升级/回退，旧0015备份不适合回退0016。

交付顺序：先完成来源字段与时效准入核验和多源摄取/预算，再节点任务UI/目录/状态，最后热门与全链验证。一版目标含公开源＋指定节点；任何节点在部署环境不可访问必须据实标明，不能悄悄降回过滤模式。目录/热门故障不得阻塞已有有效监控。

验证使用合成服务覆盖两种JSON、跨源同帖只推一次、新节点基线不吞主源新帖、首次/恢复/重启、节点删除/改名/移帖、来源暂停、10任务共享/并发保存上限、批量错峰、额度缺失/缓存旧头/429/超时/304、目录大列表与已选保留、历史诊断及四渠道；旧两站回归与amd64/arm64既定CI。真实验收只做另行授权的有限匿名可用性/元数据观察，不能通过缩短轮询对抗缓存，不发真实通知。两节点Feed一次200和程序员超时都不是长期验收。

本版仍为方案，无产品实现、迁移、部署或用户验收。当前8001维持9becf75/schema0016；热榜两旧站的分周期/自定义优化另见同日热榜说明，未混作已批准需求。
